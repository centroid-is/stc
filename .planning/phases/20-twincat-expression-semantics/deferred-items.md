# Phase 20 Deferred Items

Out-of-scope discoveries logged during execution. Each line names the plan that found it.

- **[20-02] Lexer swallows `:` after a typed literal.** RESOLVED in 20-03 (commit 9b73b57): typed literals no longer accept `:`, so `INT#5:` lexes as TypedLiteral then Colon. Time, date and time-of-day literals still keep their colons.
- **[20-02] Statement-head call with positional-first mixed args.** `fb(1, b := 2);` at statement head is not a named-arg call by the lookahead, so it now parses as an expression statement over a `CallExpr` with `NamedArgs`. It does not become a `CallStmt`. Before 20-02 it was a parse error. The interpreter and checker should treat an expression statement whose value is a `CallExpr` on an FB instance like a `CallStmt`, or the parser should fold it.
- **[20-03] fmt is not idempotent on orphan trailing comments.** Formatting st301.st or svncorecomponents.st twice moves a few end-of-block `//` comments, for example after an attribute before END_STRUCT. The output re-parses clean. The cause is comment trivia attachment, not Phase 20 nodes.
- **[20-03] TYPE blocks with several declarations.** `TYPE A : INT; B : (x, y); END_TYPE` parses only the first type and reports errors for the rest. `parseTypeDecls` handles one declaration per block. Neither oracle file uses this form.
- **[20-03] Repetition count is an integer literal only.** `[N(0)]` with a constant name `N` parses as a call expression element, not as a repetition. IEC 61131-3 allows only an unsigned integer there; CODESYS behaviour with a constant was not verified.
- **[20-04] Named VAR_IN_OUT arguments in FB calls report SEMA024.** RESOLVED in 20-06 (commit 7bc2ff5): `checkCallStmt` also searches `fbType.InOuts` for `name := value`. `checkCallStmt` searches only `fbType.Inputs` for a non-output named argument, so `fb(parameter := x)` with `parameter` in VAR_IN_OUT reports "has no input parameter". This gives 15 errors in svncore (FB_Parameter). The fix is to also search `fbType.InOuts`. It predates Phase 20.
- **[20-04] EXTENDS cycles are silent.** `A EXTENDS B; B EXTENDS A` terminates, and the edge that closes the cycle is not linked, but no diagnostic is reported. A dedicated message would need its own code.
- **[20-04] Interfaces resolve to an empty FunctionBlockType.** `i : I_Motor` checks clean, but `i.Prop` reports "has no member" because interface methods and properties are not in the type. Method calls on member callees are unchecked, so this only affects property reads.
- **[20-05] Initialised integer variables carry IECType DINT.** `w : WORD := 16#0009;` and `w := 5;` store the literal's DINT type, because initialisers and assignments do not coerce to the declared type. Runtime bit access then uses a 32-bit width for such a WORD, so `w.16` is not a runtime error there (the checker's SEMA035 still catches literal indices). Zero-initialised variables have the right type. Literal typing is RUNT-05/RUNT-06 in Phase 22.
- **[20-05] Enum tag is not kept on integer assignment.** RESOLVED by the 20-review ME-01 fix: a stored integer now takes the enum tag of the variable it overwrites, for named enum types. Inline VAR enums still start untagged. `e := 2;` on a non-strict enum variable stores a plain integer, so `TO_STRING(e)` gives '2' even with `{attribute 'to_string'}`. Values that come from `E.v`, bare `v`, `E#v` or the zero value keep the tag.
- **[20-05] Bare inline enum values are global at runtime.** Inline enums register as `<POU>.<var>`, but bare-name lookup scans every enum. Two POUs whose inline enums reuse a value name with different ordinals resolve to either one. The checker scopes them per POU.
- **[20-06] Named arguments on built-in functions report SEMA020.** `checkBuiltinCall` counts only positional `Args`, so `LIMIT(MN := 0, IN := x, MX := 10)` reports "LIMIT expects 3 argument(s), got 0". Built-in signatures carry IEC parameter names (IN, MN, MX) that the binder could use. Neither oracle file calls a built-in with named arguments.
- **[20-06] Enum value passed to an integer parameter reports SEMA021.** svncore passes an `ecfg_e` value to the UINT VAR_IN_OUT `parameter` of FB_Parameter. This surfaced once named VAR_IN_OUT binding worked. Whether a non-strict enum converts implicitly to its base integer is ruling A4, which 20-09 owns.
- **[20-06] Local VAR CONSTANT symbols are not marked IsConstant.** Only VAR_GLOBAL CONSTANT sets `Symbol.IsConstant`, so `c := 1;` on a local constant is not reported. A local constant works as a bit index only when its initialiser is an integer literal (`Symbol.HasConstInt`).
- **[20-06] Non-integer enum base types are parse errors.** The parser accepts only integer and bit-string keywords after an enum's closing parenthesis, so `(a, b) REAL` never reaches the checker's SEMA036 base-type rule. That rule only fires for ASTs built by other producers.
- **[20-07] VAR_IN_OUT and `=>` targets are evaluated twice.** The argument is read before the call and the target expression is evaluated again at write-back, so `F(io := arr[F_Next()])` writes a different element than it read. This was already true for FB call statements and now also holds for FUNCTION and METHOD calls. Binding in-outs through a `RefPath` would fix both.
- **[20-07] References stored in struct or GVL members do not auto-dereference.** `s.r REF= n;` stores the reference, but reading `s.r` or `G.r` returns the reference value and `s.r := 5` replaces it. Only identifier reference variables read and write through.
- **[20-07] Writing to an unbound REFERENCE TO replaces it.** `r : REFERENCE TO INT; r := 5;` before any `REF=` stores 5 in r, as before 20-07. TwinCAT raises an exception there.
- **[20-07] Built-in functions reject named arguments at runtime.** `LIMIT(MN := 0, IN := x, MX := 10)` is now a RuntimeError instead of being called with no arguments. Binding them needs the IEC parameter names, as for the checker's SEMA020 item above.
- **[20-09] Non-literal initialiser values are not type-checked.** `n : INT := A + 1;` is walked for undeclared names only; its value type is not compared with INT. Value checks for non-literal initialisers come with untyped literal typing in Phase 22 (RUNT-05).
- **[20-09] Real-literal arithmetic types as LREAL.** `r := UDINT_TO_REAL(x) / 5.0;` reports "cannot assign LREAL to REAL" because `5.0` is LREAL. svncore shows 13 of these now that the checker knows `UDINT_TO_REAL`, `UINT_TO_REAL` and `TIME_TO_REAL`. Literal typing is Phase 22 (RUNT-05).
- **[20-09] `[N(0)]` with a constant count is a call in initialisers.** The parser reads `[C(0)]` as a call of `C` (20-03 item). Initialiser values are now walked by the checker, so this form reports SEMA022 "not callable". Neither oracle file uses it.
- **[20-09] METHOD variable initialisers are not checked.** METHOD bodies and their VAR blocks are still skipped by the checker, so THIS^/SUPER^ and initialisers inside methods are unchecked.
- **[20-09] Initialiser and assignment literal rules differ.** An integer literal initialises BYTE..LWORD and REAL/LREAL variables (`w : WORD := 16#FF;`, `r : REAL := 0;`), but the same literal in an assignment (`w := 5;`, `r := 0;`) still reports "cannot assign DINT to WORD/REAL". Phase 22 literal typing should unify both.

## Recorded by the 20-08 phase gate

Items deferred by research or CONTEXT, plus findings from the final oracle run. Counts are from `stc check` on each oracle file alone.

- **[20-08, research Q5] Chained assignment.** `a := b := 0;` appears only in st201. It is still a parse error there. Phase 22 (stdlib parity) owns it.
- **[20-08, research Q5] Missing conversion and shift functions.** svncore reports SEMA010 for `BYTE_TO_UDINT` (6), `SHL` (3), `WORD_TO_UINT` (2), `SYSTEMTIME_TO_DT` (2), `UINT_TO_WORD` (1) and `BOOL_TO_UINT` (1). `UDINT_TO_REAL` was added by 20-09. Phase 22 owns the rest.
- **[20-08] `ADR` and `SIZEOF` are unknown to the checker.** svncore reports 10 and 5 SEMA010 for them, and `tests/twincat_probes/ptr.st` reports both. The probe still parses clean, so the fixture gate passes. Phase 22 owns built-in parity.
- **[20-08, research Q6] METHOD bodies are not checked.** Method bodies and their VAR blocks are skipped by the checker. This hides THIS^/SUPER^, named-argument and initialiser checks inside methods. Phase 22/23 owns it.
- **[20-08, research Pitfall 11] Member-callee calls are unchecked.** `checkCallExpr` returns Invalid for `inst.M(...)` and `THIS^.M(...)`, so their arguments are not bound or type-checked.
- **[20-08] Untyped integer literals widen unsigned arithmetic to LREAL.** `u := u + 1;` on a UDINT reports "cannot assign LREAL to UDINT", and `arr[(240 + u - v) MOD 240]` with UINT operands reports "array index must be an integer type, got LREAL". svncore has 21 assignments and 11 indices of this shape. Literal typing is Phase 22 (RUNT-05).
- **[20-08] Bitwise AND/OR on integer operands.** svncore reports 9 "boolean operator AND/OR requires BOOL operands" for UINT, BYTE and DINT operands. CODESYS accepts bitwise operators on any integer. Phase 22 strictness owns the vendor rule.
- **[20-08] SEMA022 cascades from undeclared FB types.** An instance whose FB type is missing (SEMA037) is reported again as "not callable (type Invalid)" at each call. svncore has 6. The call check should stay silent on Invalid types.
- **[20-08] Flattened oracle files merge their GVLs.** st301 holds 17 TwinCAT GVL files, most `qualified_only`, in one file whose derived GVL name is `st301`. Bare accesses to variables of differently named original GVLs then report SEMA033 (24). This is an input artifact. Multi-file project loading in Phase 21 removes it.
- **[20-08] Double-quoted attribute strings.** `{attribute "qualified_only"}` appears once each in st101, st201 and st301, and stc honours it like the single-quoted form. Whether TwinCAT honours it was not verified.

## Recorded by the Phase 20 code review fix

LOW findings from 20-REVIEW.md that were not fixed, plus gaps found while fixing.

- **[20-review LO-05] execCallStmt evaluates a member callee object up to three times.** The method probe, `evalMemberAccess` and `evalMethodCall` each evaluate `c.Object`, so `arr[Next()].M(x := 1);` runs `Next()` more than once. The fix is to evaluate the object once and pass the value to the method and instance paths. It touches the call dispatch of every member call, so it needs its own plan.
- **[20-review LO-06] A strict-enum error in a built-in call leaves later arguments unchecked.** `check.go` returns Invalid on the first strict-enum argument, so variables in later arguments are not marked used and can report false "declared but never used" warnings. The fix is to record the error, keep checking, and return Invalid after the loop.
- **[20-review ME-02] Enum zero value ignores a constant first value.** `zeroEnum` numbers from the AST alone, so a variable of `(ka := C_BASE, kb)` starts at 0, not 10. `E_K.ka` and `kb` are numbered from the constant. The zero-value builder has no access to the interpreter's enum definitions.
- **[20-review ME-04] EXTENDS, POINTER dereference and REF() on reduced targets.** The emitter now removes statements that use REF=, THIS^, SUPER^ or a dropped variable. It still prints `EXTENDS` on FUNCTION_BLOCK headers for schneider and portable, and it does not warn on the CLI. A vendor diagnostic channel for emit would cover both.
- **[20-review ME-03] FB calls do not require VAR_IN_OUT to be bound.** Function and method calls with named arguments now report an unbound VAR_IN_OUT. FB call statements only reject a non-variable binding, because `fb();` with in-outs bound earlier is common in existing code. CODESYS rules for FB in-outs were not verified.
