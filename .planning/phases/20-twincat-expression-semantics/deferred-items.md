# Phase 20 Deferred Items

Out-of-scope discoveries logged during execution. Each line names the plan that found it.

- **[20-02] Lexer swallows `:` after a typed literal.** RESOLVED in 20-03 (commit 9b73b57): typed literals no longer accept `:`, so `INT#5:` lexes as TypedLiteral then Colon. Time, date and time-of-day literals still keep their colons.
- **[20-02] Statement-head call with positional-first mixed args.** `fb(1, b := 2);` at statement head is not a named-arg call by the lookahead, so it now parses as an expression statement over a `CallExpr` with `NamedArgs`. It does not become a `CallStmt`. Before 20-02 it was a parse error. The interpreter and checker should treat an expression statement whose value is a `CallExpr` on an FB instance like a `CallStmt`, or the parser should fold it.
- **[20-03] fmt is not idempotent on orphan trailing comments.** Formatting st301.st or svncorecomponents.st twice moves a few end-of-block `//` comments, for example after an attribute before END_STRUCT. The output re-parses clean. The cause is comment trivia attachment, not Phase 20 nodes.
- **[20-03] TYPE blocks with several declarations.** `TYPE A : INT; B : (x, y); END_TYPE` parses only the first type and reports errors for the rest. `parseTypeDecls` handles one declaration per block. Neither oracle file uses this form.
- **[20-03] Repetition count is an integer literal only.** `[N(0)]` with a constant name `N` parses as a call expression element, not as a repetition. IEC 61131-3 allows only an unsigned integer there; CODESYS behaviour with a constant was not verified.
- **[20-04] Named VAR_IN_OUT arguments in FB calls report SEMA024.** RESOLVED in 20-06 (commit 7bc2ff5): `checkCallStmt` also searches `fbType.InOuts` for `name := value`. `checkCallStmt` searches only `fbType.Inputs` for a non-output named argument, so `fb(parameter := x)` with `parameter` in VAR_IN_OUT reports "has no input parameter". This gives 15 errors in svncore (FB_Parameter). The fix is to also search `fbType.InOuts`. It predates Phase 20.
- **[20-04] EXTENDS cycles are silent.** `A EXTENDS B; B EXTENDS A` terminates, and the edge that closes the cycle is not linked, but no diagnostic is reported. A dedicated message would need its own code.
- **[20-04] Interfaces resolve to an empty FunctionBlockType.** `i : I_Motor` checks clean, but `i.Prop` reports "has no member" because interface methods and properties are not in the type. Method calls on member callees are unchecked, so this only affects property reads.
- **[20-05] Initialised integer variables carry IECType DINT.** `w : WORD := 16#0009;` and `w := 5;` store the literal's DINT type, because initialisers and assignments do not coerce to the declared type. Runtime bit access then uses a 32-bit width for such a WORD, so `w.16` is not a runtime error there (the checker's SEMA035 still catches literal indices). Zero-initialised variables have the right type. Literal typing is RUNT-05/RUNT-06 in Phase 22.
- **[20-05] Enum tag is not kept on integer assignment.** `e := 2;` on a non-strict enum variable stores a plain integer, so `TO_STRING(e)` gives '2' even with `{attribute 'to_string'}`. Values that come from `E.v`, bare `v`, `E#v` or the zero value keep the tag.
- **[20-05] Bare inline enum values are global at runtime.** Inline enums register as `<POU>.<var>`, but bare-name lookup scans every enum. Two POUs whose inline enums reuse a value name with different ordinals resolve to either one. The checker scopes them per POU.
- **[20-06] Named arguments on built-in functions report SEMA020.** `checkBuiltinCall` counts only positional `Args`, so `LIMIT(MN := 0, IN := x, MX := 10)` reports "LIMIT expects 3 argument(s), got 0". Built-in signatures carry IEC parameter names (IN, MN, MX) that the binder could use. Neither oracle file calls a built-in with named arguments.
- **[20-06] Enum value passed to an integer parameter reports SEMA021.** svncore passes an `ecfg_e` value to the UINT VAR_IN_OUT `parameter` of FB_Parameter. This surfaced once named VAR_IN_OUT binding worked. Whether a non-strict enum converts implicitly to its base integer is ruling A4, which 20-09 owns.
- **[20-06] Local VAR CONSTANT symbols are not marked IsConstant.** Only VAR_GLOBAL CONSTANT sets `Symbol.IsConstant`, so `c := 1;` on a local constant is not reported. A local constant works as a bit index only when its initialiser is an integer literal (`Symbol.HasConstInt`).
- **[20-06] Non-integer enum base types are parse errors.** The parser accepts only integer and bit-string keywords after an enum's closing parenthesis, so `(a, b) REAL` never reaches the checker's SEMA036 base-type rule. That rule only fires for ASTs built by other producers.
- **[20-07] VAR_IN_OUT and `=>` targets are evaluated twice.** The argument is read before the call and the target expression is evaluated again at write-back, so `F(io := arr[F_Next()])` writes a different element than it read. This was already true for FB call statements and now also holds for FUNCTION and METHOD calls. Binding in-outs through a `RefPath` would fix both.
- **[20-07] References stored in struct or GVL members do not auto-dereference.** `s.r REF= n;` stores the reference, but reading `s.r` or `G.r` returns the reference value and `s.r := 5` replaces it. Only identifier reference variables read and write through.
- **[20-07] Writing to an unbound REFERENCE TO replaces it.** `r : REFERENCE TO INT; r := 5;` before any `REF=` stores 5 in r, as before 20-07. TwinCAT raises an exception there.
- **[20-07] Built-in functions reject named arguments at runtime.** `LIMIT(MN := 0, IN := x, MX := 10)` is now a RuntimeError instead of being called with no arguments. Binding them needs the IEC parameter names, as for the checker's SEMA020 item above.
